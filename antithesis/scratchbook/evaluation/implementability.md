# Implementability evaluation

> **Snapshot note (2026-10-13):** This cold lens evaluated the initial 75-property catalog and its then-current zero-callsite scan. The later shared-worktree [assertion rescan](../existing-assertions.md) found 18 startup/bootstrap/Control callsites, two partially instrumenting Control catalog properties. The final [synthesis](synthesis.md) records the 104-property result and dispositions.

This is an implementability review of all **75 canonical rows** in the [property catalog](../property-catalog.md), using the full [SUT analysis](../sut-analysis.md), [deployment topology](../deployment-topology.md), [assertion scan](../existing-assertions.md), property evidence, and the BEAM/Hegel/image/TCG/native feasibility inventories. The pinned commit is the intended source baseline; other sessions' uncommitted work is not treated as implementation evidence. There is no replacement harness, SDK assertion callsite, built hosted image, emulated guest boot, hosted run, or fresh native campaign result to credit yet. This file evaluates a path to implementing every row; it does not discard any row or classify findings for synthesis.

## Findings

### Portfolio-wide: observations and execution are separate deliverables

The topology is a sound *menu* of focused environments, but no frozen row-to-template roster exists. Each of the 75 entries needs (1) an actual command that constructs its named history, (2) an independent observation of the linearization/effect boundary, (3) a typed result for unavailable evidence, (4) a declaration and at least one meaningful SDK evaluation, and (5) an environment-specific acceptance label. The planned Python worker and BEAM fallback transport are unimplemented; the current scan found zero SDK assertions. A test template that silently omits a row because its service or emulator is absent would make catalog completeness unverifiable. Generate a manifest of all literal IDs/kinds/locations and required configurations; fail setup when a selected oracle is unavailable, and report unexercised properties separately from passing ones. See [BEAM feasibility](../beam-sdk-feasibility.md) for exact atomic JSONL, catalog-before-setup, bounded writer, and unknown-evidence requirements; [Hegel feasibility](../hegel-sdk-feasibility.md) shows local reporting probes but no hosted worker or SUT coverage.

The oracle must not infer physical success from a control response, a journal row, a diagnostic event, or a timeout. This is especially material for `lilly-interrupted-launch-at-most-once`, `lilly-outcome-replay-exact-ack`, `delete-release-follows-physical-retirement`, `ziggy-interrupted-inference-never-reexecutes`, `backup-retained-manifest-closure`, and `terminal-create-reply-loss-one-pty`. Keep attempted, acknowledged, durable, and physically observed identities in separate append-only workload ledgers, with a consistent database snapshot only for the database part. A missing read yields `unavailable`, never an empty set or an asserted zero effect. A read-only ledger needs durable state outside `ANTITHESIS_OUTPUT_DIR`, which is an output sink in the hosted environment.

The source-built release/image closure is still a prerequisite, including harness-only compile selection, exact runtime tools, final UID and private sockets, property catalog, Python SDK pin, Rust instrumentation, build IDs and `/symbols`. The [image inventory](../image-build-feasibility.md) only evaluated release derivations; it did not build OCI images. The BEAM fallback reports assertions but supplies no BEAM branch coverage; ordinary Python SDK assertions supply no Python source coverage. Neither may be counted as an exercised SUT oracle. Require a local image/Compose smoke and a small hosted declaration/evaluation smoke before broad property runs. The official fallback, setup, and test-command mechanics are cached under [SDK docs](../sdk-docs/reference--sdk--fallback.md), [lifecycle](../sdk-docs/reference--sdk--fallback--lifecycle.md), and [composer](../sdk-docs/product--writing_tests--test_templates--test_composer_reference.md).

### Control histories need a wire observer and a safe effect ledger

`control-inflight-limit-and-retirement`, `control-no-hidden-redelivery`, and `control-pending-response-retirement` require a proxy/test peer that records exact **request-frame IDs and call identity** across half-close, response loss, reconnect and late reply. The pending-map inside the client is useful SUT instrumentation but cannot by itself prove no second frame was sent. `control-bind-before-domain-effects`, `control-service-dispatch-closed`, `control-version-refusal-remains-terminal`, `execution-v4-refuses-legacy-document`, and `store-v3-host-binding-survives-upgrade` need malformed/versioned frames through the real authenticated socket or a complete Runtime restart, plus a small independently inventoried domain mutation. A synthetic direct handler call is insufficient for the transport claim. Build a bounded TLS/Control peer/proxy with reviewed fixture credentials; record the actual hello, close class, negotiated window, wire IDs and committed effect identity without recording credential bytes. Pair each refusal with a positive valid peer to prove the fixture path works. The catalog's `control-bound-credential-revalidated`, `host-credential-rotation-fences-old-socket`, and `host-session-successor-fences-old-exchanges` further need an operator rotation/successor commit barrier and post-barrier effect rows. The two Marshall containers help with cross-replica races, but a second *real* Lilly client for one host may be blocked by host-owner locking; use a protocol test peer for stale-session requests while preserving real service authentication, then use native owner evidence for the full host-client case. Source pointers and exact questions are in their property files.

`control-hint-loss-reconciles-authority` and `lost-host-hint-eventually-delivers-command` need a targeted notifier isolation that leaves Repo and at least one authority reader healthy; a generic Marshall container kill may also remove the precondition. The latter must observe the exact command's physical result, not merely a resync counter. `porsche-wait-never-resubmits-mutation` needs a count at Marshall ingress correlated with one CLI invocation and a terminal receipt; an HTTP retry count alone could miss a second mutation at another route. Instrument only fixed IDs/counters through reviewed application catalogs or a harness-local controlled peer, and use the database as independent settlement evidence.

### Lease claims need effect-boundary clocks and current authority

`audi-authority-request-start-deadline`, `lease-expiry-independent-of-blocked-renewal`, `expired-web-lease-stops-existing-guest-bytes`, `current-membership-gates-new-private-web`, and `stale-local-execution-cannot-forward-guest-bytes` cannot be established by observing an expired local timer or a closed client socket. The guest must record a fresh nonce or an upstream fixture must record first accept/read **after** the relevant committed revocation/deadline/guardian barrier. Preserve grant ID, issue/request-start time, binding, renewal result, and admitted byte/effect order with monotonic times in the same clock domain when possible; use explicit causal barriers for cross-container observations instead of comparing unsynchronized timestamps. The TCG guest plus real Audi/Lilly connector is necessary for guest-byte claims, while pure refusal branches can start in `access` without the guest. The property evidence explicitly leaves guard suspension, old-guardian death, and replayable guest endpoints unresolved; these require narrow fault/control and read-only witness interfaces, not mock guest bytes.

`galileo-accounting-delay-does-not-renew-old-grant` has a particularly concrete setup: current Marshall grant is 2,000 ms, `Overalls.RequestAccounting.Producer.admit/2` can wait 5,000 ms, and Galileo creates a fresh full-TTL deadline only afterward (`galileo/lib/galileo/http.ex:98-133`, `galileo/lib/galileo/upstream.ex:71-85,411-428`; [evidence](../properties/galileo-accounting-delay-does-not-renew-old-grant.md)). Isolate the recorder from Galileo while keeping the controlled upstream reachable, revoke or age the grant during the wait, then compare original grant return, renewal response and first upstream accept/read. The authority contract's TTL anchor remains a product-policy question; until resolved, the observation can expose the branch but cannot unconditionally label it a violation. `audi-authority-request-start-deadline` likewise retains the known 5,001–30,000 ms decoder-policy mismatch as a targeted receiver probe, not a claim that current Marshall issues long grants.

### External effects require faithful local origins and durable witnesses

`ziggy-spool-capacity-before-provider`, `ziggy-interrupted-inference-never-reexecutes`, and `ziggy-completion-once-accounted` can use real Ziggy plus one separately faultable local provider with an immutable accept ledger and Marshall aggregate snapshot. The provider must distinguish an accepted effect from a mere connection and bind it to the spool ID without exposing payloads. `galileo-accounting-delay-does-not-renew-old-grant` uses the analogous integration fixture. A lost completion ACK cannot be inferred from a generic socket reset; cut between the database commit and reply, then reconcile by immutable ID. Spool directory sync and provider acceptance need separate crash windows, and a full-slot test must use the real configured cap or state precisely that it tests only a lower-level limit.

`enrico-attempt-replay-bounded-receipts`, `enrico-native-git-admission-after-manager-restart`, and `enrico-published-head-remains-addressable` need real Git and native owner helpers, a deterministic fixed-origin DNS/TLS/smart-HTTP fixture, retained commit/blob hashes and external fetch/lock counters. A localhost URL that Enrico's fixed-source policy refuses is not a useful workload. The 1,025-completion eviction path and eight held inherited Git slots may be expensive; script small immutable repositories and pause at an actual lock/owner boundary, then measure that path rather than lowering the promised bound. Keep receipt retention scoped to the active/retained window; an Enrico restart may discard it. The local Git origin and lock files can be independent witnesses inside the hosted Linux container; they do not establish physical machine custody.

`brady-cache-complete-publication`, `brady-cache-physical-headroom-and-leases`, and `brady-listener-socket-worker-bound` need the `storage-router` TCG VM's real nftables/TPROXY path, ZFS/Brady process, source identity and an origin fixture. An HTTP success does not prove a cache hit; correlate origin count with an immutable response digest and read-only cache metadata. Worker count needs socket inode/FD inventories, not just a BEAM counter. Pressure uses fresh actual pool and guest-parent snapshots at append boundaries; the router's synthetic execution label cannot establish current per-VM authority. The [storage feasibility](../emulated-storage-feasibility.md) requires an explicit post-prepare quota, retained mirror disk files and measured three-second pressure freshness. No router VM has booted yet; a Brady property must remain unexercised if TCG cannot meet that deadline. Automatic outer faults do not isolate inner veth peers; add typed guest link/quota/QMP actions for those histories.

### Physical lifecycle and capacity need a real lower boundary

`marshall-admission-atomic-allocation` and `marshall-admission-key-survives-archive` are immediately implementable over real Marshall A/B, PostgreSQL and a controlled caller ledger, with the caveat that the archive replay leg needs an actual physical delete path. `marshall-admission-measured-physical-capacity` and `marshall-crash-recovery-budget-and-stale-capacity` additionally require the exact locked host report, holds and independent physical pool/usage sample. The control-core emulator's modeled capacities can check Marshall arithmetic and transaction order only; native ZFS/headroom acceptance needs the router/native campaign and correlated host-report freshness. Do not compare a later pool sample to an earlier allocation without preserving the report revision and causal order. A backward clock jump is not implied by ordinary network faults; tenant clock faults are unconfirmed and global, so that branch needs explicit supported fault capability or a native controlled clock test.

The full Lilly Runtime hardcodes `Executor` at `lilly/lib/lilly/control/runtime.ex:1118`; `VM.Executor` callbacks alone do not make a hosted guest runnable. The [guest feasibility](../emulated-guest-feasibility.md) identifies compile-time harness-only injection at ownership, Collector/ZFSIO and executor boundaries, with actual QEMU/backend PID, overlay, boot challenge and vsock proof. This is prerequisite for `continuing-boot-advances-generation-without-second-boot`, `guest-readiness-binds-current-physical-boot`, `lilly-async-result-keeps-command-identity`, `lilly-interrupted-launch-at-most-once`, `lilly-receipt-survives-control-loss`, `lilly-view-restart-withdraws-stream-authority`, `private-readiness-v1-gates-new-execution`, `runtime-restart-requires-fresh-readiness`, `stop-retains-disk-until-restart`, and `transient-observation-is-not-absence` as composed guest effects. The adapter must preserve real Store/actor/journal/supervisor order; a canned running row or success reply would destroy the oracle. A lower-level test can check Store/Journal refusal or exact ACK before QEMU exists, but must not claim physical guest completion.

`lilly-corrupt-intent-never-becomes-receipt` and `store-v3-host-binding-survives-upgrade` require stopping the actual host owner, editing only its fixture-owned durable command files, and restarting with host binding/version changes while keeping an independent hash of original bytes. Seed corruption only while ownership is quiescent; racing an unlocked edit against live production ownership would create a harness defect. `lilly-outcome-replay-exact-ack` needs lock-respecting journal snapshots that do not stall its race and an exact protocol ACK history. `lilly-finite-obstruction-recovery-progress` and `lilly-pool-sampling-does-not-starve-mutation` require measured quiet windows after real obstruction release; the proposed one-router VM has one pool and cannot prove two independent pool neighbors unless the fixture adds a second genuine pool or the native fleet supplies it.

`native-utility-descendant-custody` needs kernel inode/flock and descendant PID/start-time evidence after caller/helper death; ordinary Docker node death may kill the whole process tree and eliminate the intended survivor. Use an explicit process-level fault inside a persistent Linux boundary, with native NixOS acceptance for systemd/subreaper/cgroup custody. `delete-release-follows-physical-retirement`, `source-stop-after-committed-placement-holds`, `relocation-handoff-one-current-execution`, and `cancelled-relocation-restores-after-revocation` need both durable coordinator state and actual source/destination VMM, network and ZFS/transfer proof. The proposed single guest QEMU plus separate storage-router VM do not jointly implement Lilly's production ZFS-backed transfer. Add a two-Lilly native transfer fixture (or a fully typed real TCG transfer adapter with separate pools and explicit reduced claim) before evaluating the full properties. A fake import/stop receipt is not evidence of single writer or cleanup custody. Existing native transfer component tests alone do not prove Marshall handoff.

### Backup and observability have different custody from compute

`backup-interrupted-cleanup-owned-only` needs a real owned ZFS snapshot with GUID/local marker, a same-name foreign neighbor, and unavailable-inspection cuts; only the actual destruction journal plus independent post-fault pool inventory proves scope. `backup-retained-manifest-closure` requires real Restic list and isolated restore of each referenced component to recorded sentinel hashes, while shared component snapshot IDs survive retention. `backup-time-skew-never-activates-historical-authority` needs sequential guest/DB/host captures, a fenced private restore target, and live endpoint/UID reservation witnesses; the repository's restore command writes a private directory and no automatic activation path was found ([evidence](../properties/backup-time-skew-never-activates-historical-authority.md)). Implement the isolation check now; a claim about later activation needs a real documented operator path and native historical-recovery drill. Do not inject old database rows into the live primary just to trigger it. Hosted Restic/PostgreSQL can cover manifest closure, while guest/ZFS and physical authority require TCG/native evidence.

`request-recorder-capacity-does-not-admit-phantom-work` must hold 4,096 real authenticated producer tasks alive to test the declared cap, then try the 4,097th; a reduced cap tests a different claim. Measure task/FD/memory cost before putting it in a 60-minute template. `request-recorder-restart-conserves-custody` needs an independently faultable recorder with producer PID/start identity that survives its restart, plus checkpoint/finish reply cuts. `trace-archive-ack-loss-preserves-replay` and `trace-spool-physical-quota-with-retained-custody` need read-only SQLite/WAL digest and expiry observations after actual archive acceptance, a controlled export peer, and recoverable real ENOSPC/quota. A filesystem error induced only in the oracle is not a SUT storage fault; an outer process restart alone does not create an SQLite commit-uncertainty cut. All four must keep diagnostic admission separate from business effects under ADR-0149.

### Guest/workspace/terminal rows need one boot-bound witness

The hosted guest has not yet been built or booted. Its NixOS q35/PCI variant, vhost-user-vsock, TAP/private DNS, trust 1030, readiness 1024, workspace 1031, terminal 1075, editor 4444 and retained overlay are a coherent proposed path, but each is a separate bootstrap acceptance point in [guest feasibility](../emulated-guest-feasibility.md). `guest-ready-does-not-claim-workspace-checkout`, `guest-workspace-restart-publication-no-clobber`, `guest-workspace-source-replay-once`, and `source-v2-delivery-envelope-v1-boot-bound` need a guest-side append-only boot/source/HEAD/marker recorder reachable independently of Lilly's journal. Inject invalid envelope or delayed reply through a controlled real vsock responder; replacing Lilly's caller return value bypasses the protocol. Record developer edits before crash and read them before any recovery action can rewrite the checkout. `source-v2-capability-gates-admission` can initially observe real catalog/admission refusal without a guest, but its physical no-launch clause needs a disk/launch witness.

`guest-identity-cutover-preserves-uid-custody` needs a real pre-cutover database fixture and preserved pre-migration sequence/UUID/UID ledger; ordinary new-schema accounts cannot exercise the migration branch. `guest-identity-never-transfers-on-email-reuse` needs retired and replacement identities, plus actual guest home owner/read effects through at least one personal surface; database uniqueness alone cannot prove data separation. `current-membership-gates-new-private-web`, `expired-web-lease-stops-existing-guest-bytes`, and `stale-local-execution-cannot-forward-guest-bytes` require current and old boot nonce receivers with real Audi authorization and Lilly connector fencing. One TCG guest can test serial stop/start; two simultaneous old/new recorders or native relocation may be needed for overlap. Guest family claims must be repeated against NixOS and Ubuntu images where the contract is shared; a NixOS-only emulated boot does not silently establish Ubuntu behavior.

`terminal-create-reply-loss-one-pty` needs a guest counter of PTY births keyed by request ID; a final live PTY count misses create-then-exit duplicates. `terminal-input-frame-replay-once` needs an authenticated same-channel frame replay seam and guest token count/order, not a second new channel. `terminal-kill-progress-under-pty-backpressure` requires witnessing the actual blocked PTY write while a second authorized kill races; filling a viewer queue alone does not reach that lock. `terminal-physical-scrollback-budget` needs exact deque allocation/backing visibility in terminald (a narrow native probe or read-only harness hook), since RSS and the logical ring counter are too coarse. `terminal-stalled-viewer-neighbor-progress` needs a credit-stalled *open* viewer and an independently delivered neighbor nonce in a measured healthy interval. TCG resource constraints and guest terminald semantics are unmeasured; native terminal suites remain required for physical guest evidence.

### Updater and migration are native host operations

`healthy-revision-requires-live-candidate`, `migration-finishes-before-upgrade-activation`, and `updater-failed-activation-recovers-live-roles` cross systemd units, Nix closure switches, encrypted secret material and the real migrator; a Compose restart of an OTP release does not exercise those transitions. Use source-built native NixOS machine fixtures with distinct candidate closure/revision, secret-byte change, actual role health, advisory-lock/migrator process and independent unit/socket inventories. `upgrade-preserves-owned-guests` additionally needs physical VMM PID/start/cgroup and ZFS disk GUID continuity. `runtime-restart-requires-fresh-readiness` can have a hosted QEMU witness once its adapter preserves QEMU across Lilly restart, but native fleet evidence is needed for Firecracker custody. `private-readiness-v1-gates-new-execution` requires exact authenticated Ziggy/Audi-private v1 response documents, not a socket-open check. The [native inventory](../native-campaign-inventory.md) documents current fixture blockers for `service-roles`, `native-zfs` resource receipt and `zfs-io`; repairs and fresh execution are prerequisite to claiming native acceptance. The report's existing check list is evidence of test presence, not a passing current campaign.

## Passes

- The catalog usually identifies a genuine independent witness rather than treating a SUT reply as its own proof: PostgreSQL joined rows for Marshall admission, controlled upstream accept logs for Ziggy/Galileo, Restic restore hashes for backup closure, and guest nonce/HEAD for access/workspace are appropriate targets. The required interfaces are mostly **missing implementation**, not logically impossible observations.
- The focused topology separates Marshall replicas, PostgreSQL, Lilly, satellites, recorder, origin and emulator where their failure boundaries matter. It correctly says two Marshall containers over one primary do not establish database HA, and TCG does not establish Firecracker/KVM or physical host isolation.
- The catalog keeps conditional progress and refusal reachability alongside safety checks. It does not equate a lost reply with a failed effect, and its proposed source/effect IDs support deterministic reconciliation if the harness implements the ledgers.

## Uncertainties to resolve by measured implementation

- Tenant enablement for node termination, clock jumps and custom faults; hosted durable-volume and append behavior; guest/router TCG boot time, memory and three-second Brady pressure freshness. The repository and cached documentation do not establish these tenant-specific facts.
- Which full production transport seam can replay same-channel terminal frames, corrupt guest source envelopes, suspend an Audi guard, or pause a native Git owner without changing the behavior under test. Each needs an explicit narrowly scoped fixture and a positive control.
- Whether a complete 4,096-worker recorder saturation and 1,025-fetch Enrico eviction run fit focused timeline resources. These cannot be answered by reducing production limits and calling the original bound proved.
- Whether restored historical authority has a repository activation command at all; whether the Galileo TTL is defined from the original grant response; the exact guest/Ubuntu family roster; and whether two independently hosted physical machines are available for full relocation acceptance. Keep the affected branch explicitly unproven until its policy or physical precondition is established.

The report is read-only research. It changes no architectural decision or production behavior; the proposed code, deployment and verification changes require the repository's architecture, contracts and HLDD review in their implementation change.
